# Nexus HSB 功能列表与能力说明

> 本文根据当前代码库实际提供的服务入口、管理 API、协议适配器、传输层和持久化能力整理，用于描述 Nexus HSB 已具备的核心功能、相对同类软件的特点，以及各功能模块的具体说明。

## 1. 核心功能定位

Nexus HSB 是面向医院与区域医疗集成场景的服务总线平台。它的核心目标不是单纯提供通用消息转发，而是围绕医疗机构内外部系统的异构协议、系统目录、路由治理、投递可靠性和审计运维，提供一套可配置、可追踪、可扩展的集成枢纽。

当前软件实际承担的核心职责包括：

- 统一接收外围系统消息，并转换为 HSB 内部统一消息模型。
- 支持医疗常用协议与通用接口的接入建模，包括 HL7 v2、HL7 v3、FHIR R5、DICOM、SOAP、HTTP/JSON、Webhook、OpenAI 兼容端点、消息队列端点、数据库端点和自定义协议。
- 通过机构、系统、端点、Topic 和路由规则管理集成资产。
- 按源系统、协议、消息类型、Header、Payload、原始报文和业务元数据执行路由匹配。
- 将消息投递到配置的目标端点，并支持至少一次、最多一次、恰好一次等投递语义的基础实现。
- 提供管理 API 与内嵌 Web 管理台，用于配置、监控、重放、审计和运行状态查看。
- 通过 PostgreSQL 和本地 Redb 支撑持久化、恢复和幂等去重等运行能力。

## 2. 相对于同类软件的特点

### 2.1 医疗集成模型优先

与通用 ESB 或普通消息网关相比，Nexus HSB 将医疗集成中的常见对象直接建模为一等资源：机构、业务系统、端点、医疗系统类型、Topic、消息元数据和医疗协议适配器。系统天然面向 HIS、LIS、PACS、EMR、药房、医保、区域平台等场景，而不是让用户从通用队列或通用 HTTP 代理能力上重新搭建医疗语义。

### 2.2 多协议适配与统一消息模型结合

软件提供 HL7 v2、HL7 v3、FHIR R5、DICOM、SOAP 等医疗协议适配器，同时对 HTTP/JSON、Webhook、OpenAI、Database、Custom 等类型提供统一消息构建入口。外部报文进入系统后会补齐 source system、target system、message type、correlation id、trace id、headers、payload、raw payload 等信息，便于后续路由、追踪和重放。

### 2.3 管理台、管理 API 与业务入站统一出口

主 HTTP 服务同时承载内嵌管理台、管理 API 和业务消息入站接口。默认入口包括 `/ui/`、`/api/v1/...` 和 `/api/messages/inbound`，减少部署时多端口、多服务之间的运维割裂。保留独立 Admin API 端口用于兼容非 SSO 场景。

### 2.4 以治理为中心的端点与路由管理

端点不只是一个 URL，而是包含所属机构、所属系统、协议、角色、认证、连接参数、运行状态、生命周期状态、安全策略、版本快照和自定义属性。路由规则支持优先级、多目标、主备目标、匹配条件、转换器 ID、超时、确认、审计和 DLQ 选项，适合医院集成中长期维护和变更审计。

### 2.5 可靠性能力内建而非外置拼装

软件包含重试、死信队列、熔断器、端点健康状态、消息状态流转、失败原因记录、消息重放和 DLQ 重放入口。Exactly Once 投递模式在启用 Redb 幂等存储时会基于路由、目标端点和关联 ID 生成幂等键，避免同一消息重复下发。

### 2.6 面向扩展的 Rust 分层架构

项目按 common、core、adapter、transport、admin、server 等 crate 分层。协议适配器、传输层、路由器、分发器、处理管道、持久化存储和工作流执行器都通过 trait 或注册表组织，便于后续增加私有协议、新传输通道或特定医院接口。

### 2.7 对 AI 与数据源接入预留业务位置

除传统医疗系统外，端点模型已包含 OpenAI 兼容端点和数据库端点。OpenAI 端点当前按 HTTP 传输进行运行态投递，适合质控、摘要、结构化抽取、Embedding 等 AI 场景；数据库端点当前主要提供连接配置建模，运行态 SQL 投递执行层尚未完成。

## 4. 具体功能列表

### 4.1 统一消息入站处理

软件提供主业务入站接口 `POST /api/messages/inbound`。调用方需要通过 `X-HSB-Source-System` 标识来源系统，可选传入目标系统、消息类型、追踪 ID、关联 ID、优先级和协议类型等 Header。

入站处理链路包括：

- 根据 Header、Content-Type 和报文内容识别协议。
- 对标准医疗协议调用适配器解析报文。
- 对 HTTP/JSON、Webhook、OpenAI、Database、Custom 等类型构建通用消息。
- 同步 HTTP Header 到内部消息头。
- 将消息状态按 Received、Processing、Routing、Delivering、Completed 或 Failed 等阶段更新。
- 执行处理管道中的日志、指标和基础校验处理器。
- 查找匹配路由并执行目标端点投递。
- 返回 202 响应，包含 message_id、trace_id、协议、匹配路由和投递结果。

### 4.2 协议识别与协议适配

当前已注册的协议适配器包括：

- HL7 v2.x：面向传统 HIS/LIS 的 MLLP/HL7 报文。
- HL7 v3：面向 XML、CDA、区域平台类报文。
- FHIR R5：面向标准化资源交换和现代医疗应用。
- DICOM：面向 PACS/RIS 等影像系统通信。
- SOAP：面向传统 WebService 接口。

HTTP 入站协议识别规则包括：

- `X-HSB-Protocol` 优先指定协议。
- `application/fhir+...` 识别为 FHIR R5。
- 包含 `urn:hl7-org:v3` 的 XML 识别为 HL7 v3。
- SOAP Envelope 或 SOAP Content-Type 识别为 SOAP。
- `application/dicom` 识别为 DICOM。
- `application/json` 识别为 HTTP。
- 以 `MSH|` 开头的报文识别为 HL7 v2。
- 其他情况默认按 HTTP 处理。

### 4.3 端点管理

端点是一个外部系统的具体连接配置。软件提供端点的创建、查询、更新、删除、状态维护、安全配置更新、版本历史查询和健康视图。

端点模型覆盖：

- 所属机构与所属系统。
- Producer、Consumer、Hybrid 等端点角色。
- HIS、LIS、RIS、PACS、EMR、HRP、NIS、手术麻醉、药房、医保、省级平台、第三方系统等医疗系统类型。
- HTTP、Webhook、HL7V2、HL7V3、FHIR_R5、DICOM、SOAP、gRPC、TCP_RAW、MESSAGE_QUEUE、DATABASE、OPENAI、CUSTOM 等协议类型。
- 主机、端口、路径、TLS、超时、连接池、重连和 keepalive 配置。
- Basic、Bearer、API Key、OAuth2 Client Credentials、证书认证和 SSO Token 等认证方式。
- 最大重试次数、重试间隔、压缩、最大消息大小、并发限制、速率限制、熔断阈值和请求/响应体日志开关。
- secret_ref、强制 TLS、证书校验策略、IP 白名单、凭证脱敏、TLS/MTLS/SM3 等安全策略。

### 4.4 机构与集成系统目录

软件提供机构和业务系统的目录化管理，用于建立集成治理边界。

机构目录支持：

- 政府部门、医院、独立法人实体和其他机构类型。
- 父子机构关系。
- 启用状态和自定义属性。

系统目录支持：

- 系统所属机构。
- 医疗系统类型。
- Topic namespace 和 Topic prefix。
- 启用状态和自定义属性。

这一层让路由、端点、Topic 和消息追踪都能落在明确的组织和业务系统边界内。

### 4.5 Topic 目录管理

软件提供 Topic 目录 CRUD。Topic 格式固定为 `<domain>.<service>.<action>.<version>`，版本段必须以 `v` 开头。

Topic 目录用于：

- 统一业务消息分类。
- 约束医疗、AI、系统、集成等 domain。
- 标识 owner system。
- 维护 Topic 描述、启用状态和扩展属性。
- 与 NATS subject 格式兼容，便于后续事件总线扩展。

### 4.6 自定义协议管理

当标准协议无法覆盖院内私有报文时，软件提供自定义协议定义管理。自定义协议可维护协议 ID、名称、说明、传输提示、Content-Type、字段定义、样例报文和启用状态。

当前自定义协议可用于配置和治理私有报文结构；运行态直接投递 CUSTOM 目标端点尚未完成，分发器会返回协议不支持错误。

### 4.7 路由规则管理

路由定义了消息从源系统到目标端点的流转规则。软件提供路由的创建、查询、更新、删除、启用和禁用。

路由匹配能力包括：

- 源系统精确匹配或通配。
- 协议类型匹配。
- 消息类型正则匹配。
- Header、Payload、Raw Payload 和 Metadata 字段匹配。
- equals、not_equals、contains、starts_with、ends_with、regex、exists、not_exists、in、not_in、greater_than、less_than 等操作符。

路由投递能力包括：

- 多目标端点。
- 主目标、备用目标和权重目标建模。
- 路由优先级。
- 路由级转换器 ID 和目标级转换器 ID。
- At Most Once、At Least Once、Exactly Once 三种投递模式。
- 超时、异步投递、ACK、审计、DLQ 选项建模。

### 4.8 消息分发与传输

默认分发器会根据目标端点协议和地址选择传输层：

- HTTP、Webhook、FHIR R5、SOAP、OpenAI 走 HTTP transport。
- HL7 v2、DICOM、TCP_RAW 走 TCP/MLLP transport。
- gRPC 走 gRPC transport。
- MESSAGE_QUEUE 根据地址选择 Kafka、NATS 或 RabbitMQ/AMQP。
- HL7 v3 可根据地址前缀选择 gRPC、Kafka、NATS、MQ、TCP 或 HTTP。
- DATABASE 和 CUSTOM 目标端点目前不会直接运行态投递。

传输层能力包括：

- HTTP/HTTPS POST 投递、超时、连接池、代理、可控的证书校验策略和健康检查。
- TCP/MLLP 传输配置。
- RabbitMQ/AMQP 传输配置与连接。
- Kafka 生产、消费、提交 offset、基础统计和健康检查。
- NATS/JetStream 传输配置。
- gRPC 传输和 SSO 客户端配置。

### 4.9 投递语义、重试与幂等

路由可选择不同投递模式：

- At Most Once：只向第一个目标发送一次。
- At Least Once：按目标顺序尝试，失败时继续尝试后续目标。
- Exactly Once：在启用幂等存储时，使用路由 ID、目标端点和 correlation id 或 message id 生成幂等键，已处理过的消息不会重复下发。

分发器内置指数退避重试，默认最大重试次数为 3。可靠性模块还提供可复用的固定延迟、指数退避、线性增长和自定义延迟序列等重试策略。

### 4.10 消息管理与重放

管理 API 提供消息列表、消息详情和消息重处理接口。启用 PostgreSQL 持久化后，软件会保存消息状态，并在服务启动时恢复部分待处理消息。

消息查询支持：

- source_system。
- target_system。
- message_type。
- status。
- 起止时间。
- limit 和 offset。

消息重放会重新进入统一处理链路，用于处理目标系统短暂故障、路由修正或人工恢复后的补偿操作。

### 4.11 死信队列管理

软件提供死信队列模型、内存 DLQ 实现和管理 API。DLQ 支持：

- 查询死信消息。
- 查看单条死信。
- 统计死信数量、原因、源系统、目标系统和时间范围。
- 重放死信消息。
- 删除死信消息。
- 清理过期死信。

死信原因覆盖最大重试次数、消息过期、无法路由、目标不可用、解析错误、验证失败、转换失败、手动移入和其他原因。当前主 HTTP 入站失败路径会记录消息失败状态和 dead_letter_reason；DLQ 自动入队由可靠性层及相关调用路径承接。

### 4.12 审计追踪

软件提供审计服务接口和管理 API，用于查询审计事件和消息链路。审计查询条件包括 message_id、trace_id、event_type、source_system、起止时间和 failed_only。

审计事件模型包含：

- trace_id 和 message_id。
- 事件类型和严重级别。
- 发生时间。
- 源系统和目标系统。
- 组件名与描述。
- 成功标记、错误信息和耗时。

消息追踪接口可按 message_id 查询完整链路，适合排查跨系统调用失败、消息重复、路由未命中和目标投递异常。

### 4.13 熔断器与端点健康

可靠性层提供熔断器实现，管理 API 提供熔断器列表和重置接口。熔断器支持 Closed、Open、HalfOpen 状态，按失败阈值打开，按恢复窗口进入半开，并在成功次数达到阈值后关闭。

端点健康与运行状态能力包括：

- healthy 标记。
- latency_ms。
- last_error。
- circuit_state。
- consecutive_failures。
- last_check_at。
- last_delivery_at。
- 端点健康视图和状态更新接口。

### 4.14 工作流编排

软件提供工作流定义和实例管理能力。管理 API 支持：

- 工作流定义创建、查询、更新和删除。
- 启动工作流实例。
- 查询实例列表和实例详情。
- 暂停、恢复、取消和补偿实例。

工作流步骤类型包括：

- Send：发送消息到端点。
- Receive：等待响应。
- Transform：执行转换。
- Parallel：并行分支。
- Choice：条件分支。
- Script：脚本执行。
- Wait：等待。
- SubWorkflow：调用子工作流。
- Log：记录日志。

当前服务内置的工作流处理器会生成步骤执行输出并维护实例状态，适合配置和验证编排流程；具体业务发送、脚本执行等深度运行时能力可继续扩展。

### 4.15 配置与运行状态管理

管理 API 提供健康检查、就绪检查、系统状态、指标、配置查询、配置更新和配置重载接口。

系统状态包含：

- 服务状态和版本。
- 运行时长。
- 组件状态。
- 消息接收、发送、失败统计。
- 活跃路由数。
- 活跃端点数。
- DLQ 大小。
- 队列大小。

管理台运行总览会聚合机构、系统、路由、端点、消息、DLQ、系统状态和熔断器信息，便于值守人员快速判断平台运行情况。

### 4.16 安全与认证

软件在两个层面提供安全能力。

管理入口安全：

- 支持 SSO Web 登录。
- SSO 启用后，管理台与 `/api/v1` 管理 API 需要会话认证。
- `/health`、`/api/messages/inbound` 和 `/auth/...` 作为公开路径保留。
- 支持安全 Cookie、SameSite 和 state 校验。

端点连接安全：

- 支持 TLS、证书路径、证书校验策略和 MTLS/SM3 等安全算法标识。
- 支持 secret_ref 对接外部密钥系统。
- 支持凭证过期时间、最近轮换时间、轮换人和变更说明。
- 支持日志凭证脱敏。
- 支持 IP 白名单建模。

### 4.17 持久化与恢复

软件采用双层持久化设计：

- PostgreSQL：用于机构、系统、端点、路由、Topic、自定义协议、消息、工作流等持久化。
- Redb：用于本地 KV、WAL、幂等去重和部分本地运行数据。

启用 PostgreSQL 后，服务启动时会从持久化存储加载端点和路由，恢复待处理消息，并优先使用数据库存储；未启用时，管理状态可退回内存存储。

### 4.18 集群与部署基础

core 模块提供集群通信基础，面向 K8s 多副本部署场景：

- 基于 NATS 的服务发现。
- 副本状态同步。
- 集群事件模型。
- 领导选举和分布式协调的扩展基础。

仓库同时提供 K8s 部署资源和启动/停止脚本，便于在开发或部署环境中运行服务。

## 5. 当前能力边界

为准确描述软件实际能力，以下边界需要在项目介绍或售前材料中同步说明：

- HTTP 入站是当前完整业务主链路；TCP/MLLP 和 gRPC 服务当前主要提供监听骨架。
- Kafka 消费可启动并记录消息，但默认未将消费消息直接送入统一入站处理链路。
- DATABASE 端点当前支持连接配置建模，运行态 SQL 投递执行层尚未完成。
- CUSTOM 协议当前支持定义和治理，作为目标端点直接运行态投递尚未完成。
- DLQ、重试、熔断器等可靠性组件已实现，具体自动入队和熔断保护是否覆盖所有投递路径，需要按实际调用链继续接入和验证。
- 指标处理器当前是基础占位实现，管理 API 和 UI 已提供运行总览与统计展示入口。

## 6. 推荐对外描述

Nexus HSB 是一款面向医疗机构的服务总线与集成治理平台。它以机构、系统、端点、Topic 和路由为核心模型，统一接入 HL7、FHIR、DICOM、SOAP、HTTP/JSON、Webhook、消息队列和 AI 兼容接口等异构系统，提供消息解析、统一建模、规则路由、可靠投递、消息重放、死信管理、审计追踪、端点治理、工作流编排和内嵌管理台能力。相比通用 ESB 或普通消息网关，Nexus HSB 更强调医疗语义、多协议适配、可运维治理和 Rust 原生的高可靠可扩展架构。
